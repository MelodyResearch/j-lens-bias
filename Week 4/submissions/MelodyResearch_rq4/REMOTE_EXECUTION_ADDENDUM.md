# Remote-execution addendum (operational, not a protocol amendment) — 2026-10-20

`FROZEN_PROTOCOL.md` is unchanged (sha256 `2017018f…bbb2`, still enforced by the runner). No intervention outcome has ever been produced or inspected; **zero real result rows exist**. This addendum only changes *where and how safely* the frozen method runs, after the local Mac correctly stopped at 48 % free memory. Model, lens, layers (8/16/22), items, prompts, arms, outcomes, statistics, the 10 % displacement cap, and the 60 % pre-load RAM threshold are exactly as frozen.

## 1. Remote-only rule
* `--run-inference` is refused on macOS (any flags, before any model code is imported) and on any non-Linux platform. `QwenBackend` additionally refuses off Linux and without CUDA; there is no MPS or CPU inference path.
* Prepare-only, `--analyze`, `--combine`, `--validate-stage1`, and the tests remain safe locally (no torch model code runs).
* Target: a hosted Google Colab Linux CUDA GPU (free tier; no paid cloud). Nothing is "always on": Colab can refuse a GPU, idle-disconnect, or cap the session, so Stage 2 is designed to span sessions via checkpoints.

## 2. Backend adaptation
`device = cuda`. dtype = bf16 only if `torch.cuda.is_bf16_supported(including_emulation=False)` (native), else fp16 (T4-class). (Newer torch reports emulated bf16 as "supported" on T4; emulation is deliberately not accepted.) The first session pins `{code commit, config fingerprint, dtype, torch, transformers, jlens}` in `runtime_provenance.json`; later sessions must match (GPU model may differ, dtype may not) or the run refuses. Each checkpoint row also carries a `runtime` stamp (dtype, GPU, library versions, commit) and each hook record now carries layer, position and dtype. Unembedding/Jacobian direction arithmetic is done on CPU copies so tensors never straddle devices. fp16 non-finite values stop the run as before (a fail-closed outcome, not a retry).

### 2b. Repository commit pins and free-compute-only rule (operational, added before any outcome existed)
The public model and lens are requested by **exact repository commit**, not floating `main`/tag: model `Qwen/Qwen3.5-0.8B` @ `2fc06364715b967f1860aea9cf38778875588b17` (one safetensors shard, SHA-256 `04b1c301…e4696`); lens `neuronpedia/jacobian-lens` @ `16a01f309fcec900fdcec3f4cd5b64f3d00e4d5a` (the commit the released tag `qwen-n1000` resolves to; file SHA-256 `aa26b68e…c9b48`). The Colab download cell and the runtime `from_pretrained` calls use the same constants (`config.MODEL_REVISION`, `config.LENS_REVISION`); the download cell requires exactly one model shard and all four hashes. Both revisions and hashes are in `config_fingerprint()` and in `runtime_provenance.json` (pinned across sessions; the Stage 1 validator checks them). The scientific model and released lens are unchanged. The notebook also states that only an available free/no-new-payment GPU may be selected (otherwise stop; no purchases, no premium GPUs).

### 2c. Stage 1 calibration tolerance tightened (technical gate, not an outcome threshold)
Before any intervention outcome exists, the validator's norm-match tolerance (measured control displacement vs measured target displacement) is tightened from 25 % to **10 %**. It concerns only displacement magnitudes, never categories, margins or effects.

### 2d. Whole-cell safety exclusion for measured-cap breaches
A prompt/layer cell is computed in full before anything is saved. If the *measured* bf16/fp16 displacement of any arm breaches the unchanged 10 % cap (even though the intended float32 target ratio is ≤ 10 %), all five arms of that cell are recorded `safety_excluded` with the measured-cap reason, the triggering arm, the measured ratio, and the intended ratio/displacement (`cell_exclusion="measured_cap"`). The cap is not weakened and nothing becomes an `ok` row. On resume, if a cell was partially saved before a crash and a later arm then breaches the cap, only the not-yet-saved arms are excluded, leaving a mixed cell that the validator fails closed (use a fresh results directory). The validator accepts a whole-cell exclusion triggered either by intended ratio > cap or by this documented measured-cap marker.

## 3. Remote telemetry (`rq4/resources.py`), fail-closed
Pre-load: three readings 25 s apart (each logged to `rq4_memory_log.jsonl`), each requiring **≥ 60 % available system RAM** (`/proc/meminfo` `MemAvailable`, cgroup-limit aware), readable swap, PSI memory pressure `some avg10` ≤ 20 **if measurable** (`/proc/pressure/memory` may be absent), and ≥ 6,000 MB free VRAM (`nvidia-smi`). After load and after every evaluation: available RAM ≥ 30 % (unchanged), swap growth < 1,500 MB (unchanged), available-RAM drop < 2,048 MB vs the post-load baseline, PSI ≤ 20 if measurable, free VRAM ≥ 1,500 MB, torch-allocated VRAM growth ≤ 2,048 MB (the former MPS ceiling, ported). Unreadable RAM/swap/GPU telemetry stops the run. The new numeric constants (20, 6000, 1500, 2048) are operational and were chosen without any outcome. Duplicate-job (`ps`) and PID-lock checks are kept; the PID file lives in VM-local `/tmp`, because a PID persisted to Drive would be meaningless in the next session.

## 4. Persistent results and code provenance
`RQ4_RESULTS_DIR` must be an absolute path, no `..`, not inside the checkout, not under `/tmp`, `/var/tmp`, `/dev/shm`, and — if under `/content` — strictly inside a FUSE mount (Drive) listed in `/proc/mounts`; the directory must pass an atomic write→fsync→rename probe. `config.RESULTS_DIR` is taken from that variable at import; all checkpoints (`evals/`, one atomic JSON per evaluation), the memory log, preflight, provenance, approval, tables and figures live there. Model weights go to an ephemeral `HF_HOME` on the VM, never Drive.
`RQ4_CODE_COMMIT` (set by the notebook) must be a full 40-hex SHA equal to the checkout's `HEAD`; it is part of `config_fingerprint()`, so resume under another commit or config raises `FingerprintMismatch` (the commit-independent fingerprint is still used for the tracked manifests, which are byte-identical to Stage 0). Two simultaneous sessions on one folder are not lock-protected across VMs; `save_row` refuses duplicate keys, so the second writer fails rather than overwriting.

## 5. Prespecified Stage 1 validator (outcome-blind) and gate to Stage 2
`run_rq4.py --validate-stage1` (module `rq4/stage1_validator.py`) is read-only and never inspects categories, margins, rank gaps or effects. **PASS iff all hold:**
K exactly the 8 prompts / 128 planned keys, once each, valid under the current fingerprint, matching prompt hashes, no stray `.tmp`;
S every row `ok` or `safety_excluded` (any `error`, `control_degenerate`, `ineligible_pair` ⇒ FAIL); a safety-excluded cell must be the whole 5-arm cell, triggered by recorded intended target ratio > 10 % or a documented measured-cap breach (§2d), and is kept as is; every prompt needs ≥ 1 layer cell that actually ran;
C clean rows `ok`, every `ok` row has a non-empty raw generation, no hook on clean rows;
H every intervention row has `readouts` and `generate` hook calls, each fired exactly once at the row's layer and source position (= prompt length − 1);
D every measured displacement ratio ≤ 0.10 (1e-6 slack);
N random seeds 11/23/47 and sham present, norm-matched (`intended` equal to the target's to 1e-6; `measured` within **10 %** of the target's — technical calibration gate, tightened from 25 % before any outcome existed), |cos| ≤ 0.99;
F strict-JSON finite values; R runtime preflight present with finite alignment error; P provenance pins the current fingerprint, model/lens repo commits, and a bf16/fp16 dtype;
M memory log: each session that loaded the model has three ≥ 25 s-spaced passing pre-load readings, pre/post-load records, safe `after_eval` readings, and ≥ 1 `after_eval` per row (sessions refused by the pre-load gate are reported, not failed).
PASS only makes the pilot *eligible for review*. `--approve-stage1 NOTE --reviewer NAME` additionally requires a ≥ 20-character note, a fresh PASS, and records a digest of the pilot checkpoints; Stage 2 re-runs the validator and refuses if it fails, the digest changed, or the fingerprint/commit differs. The separate human/Codex reading of the raw generations remains mandatory and is not automated. A safety-excluded cell is never bypassed or replaced; a failing pilot is `PILOT_ONLY`/`BLOCKED`, and a repeat pilot after a failure needs a fresh `RQ4_RESULTS_DIR` (the failed evidence is retained).

## 5b. Resource-guard timing and resume (safety repair)
The post-load safety check uses `resources.post_load_baseline(pre, post)`: RAM/GPU-allocation baseline from the post-load snapshot (the pre-load snapshot is taken without torch, so its `gpu_alloc_mb` is null), swap baseline from the pre-load snapshot so swap growth during load is still caught. All free-memory/VRAM floors, the 60 % pre-load gate and the swap-growth ceiling are unchanged; the same baseline serves every later `after_eval` check.
`evaluate_prompt` calls the guard immediately after every actual forward pass (clean, target, each control), before the next arm starts; a failing guard raises `ResourceStop` and nothing further runs. Buffered cell rows saved later are not re-guarded (one reading per forward pass); status-only rows (excluded/ineligible/degenerate) have no forward pass and are guarded on emit. Because a cell's rows are saved atomically only after all its arms finish, a guard stop or timeout part-way through a cell discards that partly buffered cell, which is recomputed on resume; completed cells and the clean row remain checkpointed.
